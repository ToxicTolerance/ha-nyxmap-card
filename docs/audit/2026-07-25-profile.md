# Browser profile — the F3 performance findings

**Date:** 2026-07-25 · **Baseline:** v0.10.3 (`77e613e`) vs. the remediation branch
· **Branch:** `claude/code-review-documentation-1uwejg`

The [review](2026-07-25-code-review.md) and its
[remediation](2026-07-25-remediation.md) both closed with the same caveat: the
F3 performance findings were reasoned from the code and pinned by call-count
tests, but **never profiled**. This is that profile.

It changed three things. It **caught a fix that did not work** (F3(b) — shipped,
tested, and completely ineffective); it appeared to **falsify one of my own
claims** about why F3(b) mattered; and then a second pass **against a real Home
Assistant instance falsified that falsification**. The isolated benchmark was
not wrong so much as unrepresentative, in precisely the way I had flagged as its
main limitation.

Read in order: the isolated harness first, then
[Real Home Assistant](#part-2--real-home-assistant) — the correction sequence is
the point.

## Method

`jsdom` implements no layout, so measuring forced reflow there is meaningless.
This runs the **real built bundle in real Chromium** (SwiftShader WebGL), driving
the card the way Home Assistant does.

- **Two bundles, same harness.** `vite build` at `77e613e` (pre-fix) and at the
  remediation HEAD, loaded into an identical page.
- **Hermetic.** A minimal MapLibre style (`version: 8`, one background layer, no
  sources) is served from loopback. No tiles, no network, no CDN.
- **One "tick" = one new `hass` object**, which is what HA hands out on every
  state change anywhere in the instance. Entity positions are *identical* every
  tick and one unrelated sensor changes — the ordinary steady state, and exactly
  the case the fixes target.
- **Counters are deterministic**, and are what the conclusions rest on:
  `getComputedStyle` and `Element.prototype.getBoundingClientRect` are wrapped
  before the bundle loads, and `GeoJSONSource.prototype.setData` is wrapped
  through the card's own plugin hook (`nyxmap-map-ready` hands out the bundled
  `maplibregl`, which is the only way to reach it from outside the bundle).
- **Layout/style-recalc counts come from CDP** `Performance.getMetrics`
  (`LayoutCount`, `RecalcStyleCount`, `LayoutDuration`, `RecalcStyleDuration`,
  `ScriptDuration`).
- 30 warm-up ticks, then 300 measured; median of 5–7 runs.

### The harness had to be fixed twice before it measured anything

Recorded because the first two runs produced confident, wrong numbers:

1. **Every entity was being clustered.** At the default `globe` projection and a
   fitted low zoom, all ten markers landed inside cluster touch distance, so
   they were absorbed — which meant `CircleRenderService` skipped all of them
   and **not one accuracy circle existed**. `setData` read `0` in both bundles
   and looked like "no difference". Fixed with an explicit camera
   (`projection: mercator`, `x`/`y`/`zoom`, a 600px-tall card) and wider entity
   spacing.
2. **No validation that the run exercised the code under test.** Each run now
   asserts its own shape — 11 overlays (10 circles + clusters), 0 absorbed, 10
   markers — and the runner flags any run that differs. Both bundles report
   identical shape, which is what makes the comparison legitimate.

## Results

### 10 entities · 300 ticks · median of 7 runs

| Metric | before | after | change |
|---|---|---|---|
| `getComputedStyle` calls | 300 | **1** | −100% |
| `getBoundingClientRect` calls | 900 | **0** | −100% |
| `GeoJSONSource.setData` calls | 3000 | **0** | −100% |
| Layout count (CDP) | 0 | 0 | — |
| Style recalc count (CDP) | 0 | 0 | — |
| Script duration | 24.6 ms | **2.0 ms** | −92% |
| Wall time | 201 ms | 127 ms | −37% |

### 30 entities · 300 ticks · median of 5 runs

| Metric | before | after | change |
|---|---|---|---|
| `GeoJSONSource.setData` calls | 9000 | **0** | −100% |
| Script duration | 66.9 ms | **4.5 ms** | −93% |
| Wall time | 559 ms | 449 ms | −20% |

The call counts are exact and reproducible: `setData` is precisely
`entities × ticks` before and zero after; `getComputedStyle` is precisely one per
tick before and one in total after. **Script duration** is the honest headline —
the per-tick JavaScript the card runs when nothing it displays has changed fell
by roughly an order of magnitude.

**Wall time is noisy and should not be quoted precisely.** Individual "before"
runs at 10 entities ranged 120–242 ms with a bimodal shape, under SwiftShader in
a container. Run shape was verified identical across every run, so this is
scheduler/GC noise rather than a difference in work. The direction is consistent;
the magnitude is not trustworthy to better than "meaningfully lower".

## Part 1 correction: F3(b)'s mechanism, as it looked in isolation

> **Superseded by Part 2.** The conclusion in this section is correct *for an
> isolated page* and wrong as a general claim. Kept as written, because the
> reasoning error — generalizing from a harness that contained nothing but the
> card — is the useful part.

The review said the switcher's three `getBoundingClientRect()` calls were "a
forced synchronous layout, per card, per tick". **The profile says otherwise.**
`LayoutCount` and `RecalcStyleCount` are **0 in both bundles**.

The CDP counters are not broken — a control probe (dirty a node, read its rect,
200×) reports exactly 200 layouts and 200 style recalcs, and a read-only probe
reports 0. So the result is real: in the steady state Lit's re-render of the
switcher wrote **no DOM mutations** (every bound value was identical), nothing
invalidated layout, and the three rect reads hit cached geometry.

So — in this harness — the true cost of F3(b) was the Lit update machinery plus
three cheap reads, visible in `ScriptDuration`, not in layout.

The last sentence of that paragraph originally read: *"A forced layout would
occur if something else on the page dirtied the DOM between the switcher's write
and its read, which is plausible on a busy dashboard — but that is not what I
measured, and I am not claiming it."* That hedge turned out to be the whole
story. See Part 2.

## The fix that did not work

`getBoundingClientRect` came back **900 → 900, unchanged**, against a bundle that
already contained the F3(b) fix, had a passing regression test, and was described
in the changelog as fixed.

Memoizing the item arrays was necessary but not sufficient. `render()` also
passed three freshly-created arrow functions:

```ts
.onSelectBaseStyle=${(id: string) => this._onSelectBaseStyle(id)}
.onToggleOverlay=${(id: string) => this._onToggleOverlay(id)}
.onSelectThemeMode=${(mode: ThemeMode) => this._onSelectThemeMode(mode)}
```

A new function instance fails Lit's identity check on its own, so the switcher
updated on every tick no matter what the arrays did, and `updated()` re-measured
every time. Binding the three once as arrow-function fields took the count to 0.

The array-identity test passed throughout, because it asserted the thing that was
fixed rather than the outcome that mattered. There is now a test asserting
callback identity directly, and it fails against the previous commit.

## Reproducing

The harness is not committed — it depends on `playwright` and a Chromium binary
that are not project dependencies, and it compares two builds of the same repo.
To rebuild it: serve a minimal style JSON and both bundles over loopback, mount
`<nyxmap-card>` with `layer_switcher: true`, `cluster_markers: true`,
`show_accuracy_circles: true`, `projection: mercator`, an explicit camera and a
600px height; wrap the three counters before the bundle loads; drive N ticks of
fresh `hass` objects awaiting `updateComplete`; and read CDP
`Performance.getMetrics` either side. Validate overlay/marker/absorbed counts per
run before believing any number.

# Part 2 — Real Home Assistant

**HA core 2024.3.3, frontend 20240307.0**, running headless from a venv, onboarded
over its own API. The card is installed the way a user installs it: the built
bundle dropped in `config/www/` and registered as a Lovelace **JavaScript Module**
resource. It renders in a real masonry dashboard **alongside four real HA cards**
(two `entities`, a `history-graph`, a `markdown`) which dirty the DOM on the same
main thread — the condition Part 1 could not reproduce.

Nothing is synthetic here. A "tick" is a genuine state change POSTed to
`/api/states/sensor.unrelated`, delivered to the browser over HA's own WebSocket,
turned into a fresh `hass` object by HA's frontend and handed to the card by
Lovelace.

**HA does not coalesce.** The card's `updated()` ran exactly **300 times for 300
state changes**, in both bundles. The premise the whole F3 group rests on — that
the card re-renders on every state change anywhere in the instance — is now
measured rather than assumed.

## Results · 300 real state changes · median of 3 runs

| Metric | before | after | change |
|---|---|---|---|
| card `updated()` calls | 300 | 300 | 0% |
| `getComputedStyle` calls | 302 | **35** | −88% |
| `getBoundingClientRect` calls | 900 | **0** | −100% |
| `GeoJSONSource.setData` calls | 3000 | **0** | −100% |
| **Layout count** | **111** | **32** | **−71%** |
| **Style recalc count** | 112 | 33 | −71% |
| Layout duration | 28.5 ms | 8.6 ms | −70% |
| Style recalc duration | 6.7 ms | 2.1 ms | −69% |
| Script duration | 80.5 ms | 35.3 ms | −56% |
| **Task duration** (total main thread) | **1117 ms** | **506 ms** | **−55%** |

Run shape was identical across every run and both bundles: 11 overlays, 10
markers, 0 absorbed, 4 sibling cards.

`getComputedStyle` lands at 35 rather than 1 because the rAF coalescing admits
one read per frame and a real run spans many frames — which is the intended
behaviour, not a shortfall.

## The correction, corrected

**In real Home Assistant, layout *is* forced — and it was the layer switcher
doing it.** Part 1 measured `LayoutCount: 0` and I concluded the forced-layout
claim was wrong. That conclusion was over-generalized from a page containing
nothing but the card.

An ablation settles the mechanism. Same **pre-fix** bundle, same 300 real state
changes, only `layer_switcher` turned off:

| Configuration | `getBoundingClientRect` | Layout count | Layout ms | Script ms | Task ms |
|---|---|---|---|---|---|
| before, switcher **on** | 900 | **111** | 28.5 | 80.5 | 1117 |
| before, switcher **off** | 0 | **10** | 3.4 | 81.4 | 1121 |
| after, switcher on | 0 | 32 | 8.6 | 35.3 | 506 |

Removing the switcher removes ~101 of the 111 layouts and 25 of the 28.5 ms,
while **script and task time are unchanged** (81.4 vs 80.5 ms; 1121 vs 1117 ms).
So the switcher's per-tick cost was almost entirely *layout*, not script — and
the residual script/task cost in the pre-fix bundle is the circle `setData` churn
and the theme read, which is what the other two fixes address.

The original review's wording — "a forced synchronous layout, per card, per
tick" — was therefore right in substance, with two qualifications the profile
adds: it needs sibling cards dirtying the DOM to happen at all (so it is a
*dashboard* effect, not a card-in-isolation effect), and it was ~1 layout per 2.7
ticks rather than one per tick.

**Caveat on the ablation:** turning `layer_switcher` off removes the switcher
element entirely, not just its three rect reads, so it also shrinks the DOM
slightly. It isolates "the switcher's per-tick behaviour" rather than "those three
calls specifically". The 900 → 0 rect reads moving in lockstep with 111 → 10
layouts is strong, but it is not a single-variable experiment.

## Reproducing Part 2

Not committed, for the same reason as Part 1 — it needs Playwright, a Chromium
binary and a full HA install, none of them project dependencies. The shape:
`uv venv` + `uv pip install homeassistant` (Python 3.11 resolves to 2024.3.3;
pin `josepy==1.14.0` or the `forwarded` middleware's `hass_nabucasa` import dies
on `acme`), a minimal `configuration.yaml` with `frontend`/`api`/`websocket_api`
(**not** `default_config`), onboard over `/api/onboarding/*`, create entities via
`/api/states/*`, register the bundle through the `lovelace/resources/create`
WebSocket command and save a dashboard with `lovelace/config/save`. In the
browser, seed `localStorage.hassTokens` — it must include `hassUrl` or the
frontend bootstrap throws — and install the counters via `addInitScript` so they
are in place before the bundle loads. Serve the map style from `config/www/` so
the run is hermetic.

## Still not covered

SwiftShader is not a real GPU, so nothing here measures MapLibre's own render
cost. The dashboard is four sibling cards, not a heavy real-world one. And
`npm audit` / supply chain remains unexamined.
